# roma: design

A YouTube Music client for Android, Linux and Windows. It shows a romanized form of every non-Latin string, and its controls never move.
Working name; rename freely.

## Rules

- No exceptions fitted to examples. Romanization and lyrics logic use general rules (a script, a part of speech, a sound rule, a standard) and data from their sources; never a list of words or songs that happened to come out wrong. A wrong result for one song or word is a user correction or a dictionary limit, recorded as a known limit if it matters. (User, 2026-10-24.)

## Scope

- Android first. Test devices: Zenfone 10 and a Huawei MatePad on EMUI, which has **no Google Play Services**. Never depend on GMS.
- Desktop: Linux and Windows (2026-10-29), the same screens and logic as Android; see Desktop below. `core` (data, romanization, lyrics) imports no Android API.
- Language: Kotlin, because Media3 fits best. The user isn't keen on Kotlin, so keep the code plain. No Flutter, no Kotlin Multiplatform: the shared code is one source folder compiled into both apps (Desktop).
- Not in v1: offline downloads (the stream cache is enough), a separate tablet layout (the MatePad uses the phone layout; only landscape puts the controls beside the upper area), video playback, the mini player.

## Romanization

- Convert once, when metadata enters the app, and store `original` + `latin` next to each other. Every surface reads from the stored pair: lists, player, queue, search, lyrics, MediaSession metadata, notification. No surface romanizes on its own.
- Order of preference for names:
  1. An official Latin name (YouTube artist channel name, a MusicBrainz alias if it's cheap to get).
  2. A user override.
  3. Machine romanization.
- Machine schemes, user-selectable per script:
  - Japanese: Modified Hepburn by default; option for no macrons.
  - Korean: Revised Romanization.
  - Chinese: pinyin with tone marks by default; option for no tones.
  - Cyrillic: the language is read from its distinctive letters (below). Russian: English-style by default; options for Polish-style and ISO 9. Other languages use their national Latin form; the ISO 9 option applies to every language.
  - Greek: a classical scheme without accent marks by default (β = b, βίος → "Bios"): ICU's `Greek-Latin` with its marks removed. Option for modern Greek, ELOT 743 (β = v): ICU's `Greek-Latin/UNGEGN` without its macron below (η = i̱), which only serves reversibility. ICU was checked first; it gives the right letters, so no table of our own.
  - Other scripts: ICU defaults.
- Han text, Japanese or Chinese? Decide in this order:
  1. Kana in the string means Japanese.
  2. Kana in a sibling field (artist, album) means Japanese.
  3. With Japanese as the default, Chinese evidence in the string or a sibling means Chinese (`Romanizer.looksChinese`), from standards and the dictionary, never from a list of words: a Han character outside JIS X 0208, Japan's standard character set (說, 你, every Simplified form); a Han word the Japanese dictionary doesn't know (瓷); or three one-character Han words in a row, since Chinese names and phrases fall apart into characters (周|杰|倫, 不|會|飛) where Japanese compounds are dictionary words. Variant forms Japanese names use (﨑, 𠮷) are never evidence. Measured 2026-10-28: none of 120 Japanese titles and names without kana matched; about 60% of Chinese titles did, and most Chinese artist names, which then decide all their songs. The dictionary's two rules need the dictionary.
  4. Otherwise use the user's default language (setting). Known limit: a Chinese title that is also a Japanese word (晴天, 江南), by an artist with no evidence, is read as Japanese.
  - In lyrics this is decided once per song, from the whole lyrics: kana in any line makes every line Japanese, so a kanji-only line in a J-pop song by a Latin-named artist is still read as Japanese; otherwise Chinese evidence in any line makes every line Chinese.
- Capitalization:
  - Titles and names get title case. Japanese particles (part of speech 助詞 in Sudachi, and だ as に/な/で after a na-adjective) stay lowercase: "Yoru ni Kakeru", "Kimi no Na wa". Korean, Chinese and other caseless scripts capitalize every word ("Qíng Tiān": Chinese stays one word per syllable). Cyrillic and Greek keep the original's capitals ("Gruppa krovi").
  - The first word is always capitalized, in any script (βίος → "Bios", "の歌" → "No uta").
  - Lyric lines get sentence case: only the line's first letter is capitalized ("Shizumu yō ni"). Title case on every lyric line reads like a list of headlines.
  - Parts that were Latin already never change ("LiSA", "feat.", "(Ballade Ver.)"). A user correction is shown exactly as typed.
- Japanese word spacing: auxiliaries, suffixes, a prefix, the te-form and ば attach to their word ("aruita", "aruite", "tabemasu", "okāsan", "sannin", "ikeba"); です, でしょう, だ and らしい stay apart ("iku deshō"). A subsidiary verb straight after a verb stem glues ("hashiridasu"); after the te-form or an adjective it is its own word ("tokete yuku", "tabete iru", "tsuyoku nareru"). Contractions such as てる and ちゃう are auxiliaries, so they glue ("tabeteru"). A sentence-final particle at the start of a phrase is a misread first syllable and joins the next word (よ|ふかし → "Yofukashi").
- Japanese readings: Sudachi's reading is the kana spelling, so Hepburn's spoken forms come from spelling plus part of speech: particles は へ を → wa e o; オウ, オオ, ウウ inside a word → ō, ū (tōkyō, ōkii, kūki), while エイ and イイ stay (eiga, ōkii); a verb's final ウ is its ending, not a long vowel (omou), except in the volitional (ikō); katakana ー → macron (kōhī). 何 is nan before t, d and n sounds and as a number (nan de, nando), else nani. Readings come from the dictionary alone: no word lists. Where the dictionary's reading isn't the one a song uses (明日 asu/ashita, 私 watakushi/watashi), that is a correction. The kana spelling is kept where Hepburn would need morpheme boundaries the dictionary doesn't give (お母さん okaasan: aa → ā would also turn 場合 baai into "bāi"). A reading in brackets after a word (君(きみ)) is dropped.
- Mixed script:
  - Before romanizing, the half-width and full-width forms block (U+FF00–U+FFEF) is NFKC-normalized: ＬＯＶＥ → LOVE, ｱｲ → アイ, （ → " (". Only that block: full NFKC also changes Latin text (² → 2, ﬁ → fi) and kaomoji (´ becomes a space and an accent).
  - Japanese punctuation becomes Latin: 、 → ","  。 → "."  「」『』 → `"`  ・ → space (only between two words)  ～ 〜 → "~".
  - Strings are read by code point, so 𠮷 is Han and an emoji doesn't make a title non-Latin.
- Stylized text stays as is:
  - A word that mixes Latin letters with Greek or Cyrillic letters is not romanized ("ΛRCTIC", "ЯOCK", "μ's"). Only Greek and Cyrillic: Japanese mixed with Latin is normal and is romanized ("Bokura no LIVE").
  - A single Greek or Cyrillic letter between symbols, with no space or line edge on either side, stays: (´・ω・`) keeps its ω. One-letter words between spaces are romanized (Russian я, и, в).
  - Known limit: inside Japanese text, Sudachi splits "ΛRCTIC" into Λ and RCTIC, so the rule doesn't hold there.
- A title's own Latin form: when a song or album title carries one after " - ", " / " or in parentheses, and that part is fully Latin, the Latin form is just that part ("スピカ - Spica" → "Spica"). A part that looks like a version tag (ver, live, remix, feat., TV size, …) doesn't count, so "(Ballade Ver.)" is kept. Artist names don't get this rule ("… - Topic").
- Overrides: the user can correct any string. Scope is this string, this song or this artist. Stored locally and exportable as one file.
- Word readings (scope "word"): the reading of one word, in one song or everywhere (私 → watashi where the dictionary says watakushi). It applies inside any string, titles and lyric lines alike, wherever the word is a whole dictionary token or a run of whole tokens; never inside a longer token (私立 stays shiritsu). Japanese matches Sudachi tokens; other scripts match a word between spaces or a run of one script. A song's own reading wins over the everywhere one. Title and sentence case apply to it like any word. Set from a long-press on a lyric word or from the correction dialog's word buttons; listed in Settings and part of the export.
- Scripts you read (setting, none by default): text only in those scripts shows as written, in lists, the player, the notification and the lyrics (no romanization line).
- Display modes: Romanized, Both (Latin with the original small underneath), Ruby (reading above the original), Original. One setting places romanization everywhere: under the original (Both, and a line under each lyric line; the default), above each word (Ruby in lists, the player and lyrics), or custom, which shows a choice per surface: lists, the player (any of the four modes) and lyrics (a line under, or above each word). Someone who had set a per-surface choice before that setting existed starts on custom.
- Search: the local index includes the romanized forms, so "kimi no" finds 君の声. Remote search sends the query as typed; YouTube's own spelling correction applies (see Search).

## Lyrics

- Every enabled provider is asked at once, each for at most 5 s (`LyricsProviders.find`). YouTube Music's own text is the reference, and the first rule that holds picks the lyrics (`chooseLyrics`):
  1. Word-level (karaoke) from any provider whose text matches YTM's. When YTM has no lyrics, any word-level result.
  2. YTM's line-timed lyrics.
  3. A third-party line-synced result whose text matches YTM's.
  4. YTM's plain lyrics.
  5. Only when YTM has nothing: third-party synced, then third-party plain, in the user's provider order.
  - Among several matching candidates in rules 1 and 3, the most similar wins, then the user's order.
- "Matches": `similarity` > `SAME_LYRICS` (0.6). Both texts are normalized (NFKC, lowercase, letters and digits only; Traditional Chinese folded to Simplified through ICU) and compared as the Dice coefficient of their character bigrams over the whole lyrics. Bigrams, not edit distance, because providers differ in whether repeated choruses are written out. Measured 2026-10-24: the same lyrics from two providers 0.77–1.00 (credit lines and Traditional/Simplified differences at the low end); LRCLIB's other-language Lemon 0.00; a different song in the same language around 0.3.
- Providers sit behind one small interface, so you can add or reorder them. Settings list the providers in order, each with an on/off switch. The order only breaks ties in rule 5.
- Translations are a separate layer (`Translation`: source, language, lines of original text + translation), not part of the chosen lyrics. Every provider result with a translation gives one layer; Google Translate, on the user's tap, adds another. At display time the layer in the first wanted language that has one is picked (the device language before English; the lyrics' own source first, then the first found) and attached line by line (`attachTranslation`): same normalized original text first, then, when both are synced, the line starting within 1 s. Lines with neither get none.
- Cache: cacheDir/lyrics/<videoId>.json holds a `LyricsResult` (the chosen lyrics without translations, every translation layer, the rule). A result is cached; "no lyrics" is cached only when every provider answered. If any failed or timed out, an empty result is not cached and the next play asks again.
- The end of the lyrics shows "Lyrics: <source>" and "Translation: <source>" in small text. YTM's source keeps its own source message ("YouTube Music · Source: LyricFind").
- Display per line: original, romanization, translation (if available). Each layer can be turned on or off. In karaoke mode, highlight the current word in **both** the original and the romanization: romanize per token so the timings map 1:1.
- Translations show only when their language matches the "Translation language" setting: by default the device language, then English. KuGou and NetEase send Chinese translations; LyricsPlus sends Apple Music's English ones where Apple has them. The language is read from the script: Han is Chinese, kana Japanese, Hangul Korean, Cyrillic Russian, Latin English. A song whose translation doesn't match shows no translation layer, unless the user asks Google for one. The "Show translation" switch is a global setting and is never dimmed by the current song.
- Google translation is per song and only on a tap, since it sends the lyrics to Google (an unofficial, keyless endpoint, `GoogleTranslate`; it may break). The lyrics view has a fixed "Translate" chip at its top right: it asks for the lyrics in the first translation language and keeps the layer with the song's cached lyrics, so it shows on every later play ("Search lyrics again" drops it). It is dimmed while it works, once the song has a translation in that language, when it has no lyrics, or when "Show translation" is off. Google answering that the lyrics are already in that language, or no connection, is said in a toast. A line Google returns unchanged gets no translation.
- Tapping a line seeks to it. Long-pressing a word (in either layer) opens its card: the dictionary's kana, romaji, dictionary form and part of speech, and the user's reading for this song or everywhere (the scope last used is offered first), or Keep original. The word is the dictionary word under the finger, not the karaoke syllable: し in 忙|し|い opens 忙しい.
- Each line is also split into words as its romanization spaces them (`Romanizer.pieces`: a word with its glued endings, particles apart). The "Above each word" layout sets each word's romaji right above it (ruby); in karaoke the word holding the current syllable is lit.
- Long-pressing the player's title or artist opens the correction dialog.

## Controls: fixed positions

The core rule: **a control never moves.** If a feature is unavailable, its button stays in the same place, dimmed. No action bar scrolls sideways. The playback source (playlist, album, radio, search) never changes the layout.

Bottom block of the player, the same on the song, lyrics and queue views (only the area above it changes). Changed by the user on 2026-10-24 to a shorter block with play nearest the thumb; positions are fixed again from there:

```
[ 0:42 ][ seek bar ][ 3:16 ]                                   about 28 dp
[ More ] [ (empty) ] [ Comments ] [ Lyrics ] [ Queue ] [ Like ] about 44 dp, small icon, 10 sp label
[ shuffle ] [ prev ] [ PLAY/PAUSE ] [ next ] [ repeat ]        about 52 dp, play icon 44 dp
[ Home ] [ Search ] [ Player ] [ Library ] [ Settings ]        bottom navigation, about 48 dp
```

- The elapsed and total time sit on the seek bar's line. Every slot is at least 48 dp wide. No extra gap between the rows.
- The action row has 6 equal slots. Slot 2 is deliberately empty: no icon, no label, not tappable. It keeps More (which holds Ban) away from the other buttons. Slot 3 was empty too until Comments took it (user, 2026-10-26).
- Left-handed mode (setting) mirrors the action row: Like on the left, More on the right. Nothing else moves.
- On a landscape screen (a phone on its side, the MatePad) the upper area is on the left and the same block, in the same order, on the right. On a wide portrait screen the block keeps at most 560 dp of width, centred.
- The Never button was removed (user, 2026-10-24). Ban song / Ban artist live in More; banning the playing song skips it and shows a "Banned · Undo" bar for about 5 s.
- Lyrics, Queue and Comments are toggles that swap the upper area. The selected one is highlighted. Lyrics is dimmed when no provider has lyrics.
- Comments: the song's YouTube comments (top first) through the WEB client's `next` and its continuations (`roma.core.Comments`), a page of 20 at a time as the list scrolls; kept while the song plays. Text with non-Latin letters in a script the user doesn't read shows its romanization (sentence case) above the original. A comment with replies has an "N replies" button that opens its thread underneath, indented, a page at a time ("More replies"); YouTube nests replies one level only. A song with comments turned off says so. A fixed "Translate" chip at the top right, as in the lyrics, shows each comment's Google translation (first translation language) under it; it is a toggle ("Original" turns it off), kept while the song plays. Only after that tap, each comment and reply is sent on its own as it comes into view, since comments mix languages and Google detects one per request. A comment already in that language gets none.
- On the song view, tapping the title opens its album and tapping the artist opens the (first) artist's page, as More → Go to album / Go to artist do; long-pressing either still opens the correction dialog. Back from a page opened from the player returns to the player.
- Like is always the rightmost slot.
- No mini player. The bottom nav has a Player tab to get back to the player.
- Notification / lock screen (MediaSession): prev, play/pause, next, Like as a custom action. No ban button there. Title = Latin form; artist line = artist + original title.
- The ⋯ menu on a song has the same items in the same order everywhere.
- Bottom nav: Home, Search, Player, Library, Settings, in a fixed order, Player in the middle. Player is dimmed when nothing is loaded. Back (or a swipe down on the song view) leaves the player for the tab it was opened from.
- Gestures add shortcuts and never move a control (2026-10-24): on the song view, swipe sideways for the next or previous song (the target peeks in during the drag; it goes to the song before even past 3 s, as the peek shows), double-tap to like (only likes, never unlikes), swipe down to leave the player. Long-press play/pause for the sleep timer (15 min to 1.5 h, or when this song ends; the last 10 s fade out); while it runs a chip at the top of the upper area shows the time left.
- Seek bar: while dragging, the lyric line at the drag position shows over the bottom of the upper area; near a timed line's start (12 dp of travel) the drag snaps to it with a haptic tick.
- Haptics: like (button and double-tap), ban, a swipe passing the skip point, a seek snap.
- Lyrics view background: the song's art, blurred (Android 12+; a 16 px copy stretched on older versions) at 20 % opacity, fading into the theme's background at the top and bottom.
- Long lists (library, album and playlist pages, the queue; over three screens) show a fast-scroll thumb on the right edge while they scroll and for 1.5 s after. Only then does it take touches, so the rows' ⋯ buttons under it work otherwise.
- Display options, off by default: true black in dark mode (OLED), and an accent colour from the playing song's art (a saturation-weighted average of a 24 px copy; grey art keeps the usual colours).
- Large system fonts: the fixed rows (player controls, nav bar) follow the font size up to 1.3×, so their labels and times are never cut off; everything else scales fully. Search filters wrap onto a second line in the same order.
- Settings: the tab shows one row per category (YouTube, Romanization, Lyrics, Queue and radio, Appearance, Banned, Last.fm), each with what it holds now (sign-in, the placement, the number of corrections, whether Last.fm scrobbles). A row opens its page on the Settings tab's stack, so Back returns to the list. Romanization holds everything about it: its placement, the schemes, scripts you read, the dictionary, and Corrections one level deeper. An available update shows above the categories.
- Errors say what to do: no connection → "Check Wi-Fi or mobile data, then Retry"; a timeout → "Retry in a moment". A song that can't play offers Retry and "Play the next song".

## Queue and radio

- The queue has 3 sections: Now, You queued (pinned: radio never reorders or removes these), Radio.
- Each radio item shows why it's there ("same artist", "often played after X") when the API provides that.
- Tapping a song in search results or a Home shelf plays that song alone; YouTube's autoplay (radio) follows. Only album and playlist pages queue the rest of their list.
- Radio leash setting: how far the radio may drift from the seed (close, medium, free). Default is free: YouTube's autoplay as is. The simplest thing that works: when close, filter radio results to the seed's artist and related artists.
- Filters, each a setting and all on by default:
  - Prefer audio tracks over music videos.
  - Hide duplicates: live, sped up, nightcore, slowed.
  - Skip banned songs and artists.
- Option: stop when the queue ends (no autoplay).
- Playback: gapless; loudness normalization if the stream provides loudness data.

## Last.fm

- In-app scrobbling: browser auth flow to get a session key; `track.updateNowPlaying` and `track.scrobble`. Follow the standard rules: the track is longer than 30 s, and it was played for half its length or 4 min. Keep an offline queue and send it in batches of up to 50.
- Scrobble the **original** metadata, not the romanized form, so tracks match Last.fm's database.
- The user registers their own API key and secret in settings. Don't ship one.
- Not in v1: recommendations. The API no longer has a per-user recommendation endpoint. Doing it ourselves means `track.getSimilar` from the user's top tracks, then matching each result to a YT Music track, and the matching is the hard part. A possible later radio source.

## Search

- Filters in a fixed order: Songs, Albums, Artists, Playlists. Videos are excluded by default.
- Results show Latin with the original underneath.
- Spelling (checked 2026-10-24): YouTube Music corrects typos with and without the Songs filter. "yoasbi yoru ni kakru" and "kenshi yonezy lemon" come back as results for "yoasobi yoru ni kakeru" and "kenshi yonezu lemon" (`showingResultsForRenderer`); "kino grupa krovi" comes back for the query as typed, which already finds Группа крови, plus a suggestion "kino gruppa krovi" (`didYouMeanRenderer`). Both sit in an `itemSectionRenderer` before the results, which innertube used to drop; the vendored `YouTube.search` now reads them (`SearchResult.correctedQuery`, `autoCorrected`, `originalParams`). This is the only change to the vendored innertube.
- One line directly above YouTube's results (under the filters, or under the "Seen before" rows when there are any) shows the correction: "Showing results for “X” · Search as typed" (the corrected query gives way to "…" so the action always fits; tap: search the query as typed, with YouTube's `originalQueryEndpoint` params, which turn the correction off for that filter) or "Did you mean X?" (tap: search X). Changing the filter or the query clears the "as typed" choice.
- Suggestions: while the text differs from the last search, YouTube's suggestions (`searchSuggestions`, 250 ms after the last keystroke) take the results' place; tapping one searches it.
- "Seen before" lists only songs played past the scrobble point (half the song or 4 minutes; ids in filesDir/played.txt, kept across cache clears); every other song seen in results only ranked the list poorly. Matching ignores case, accents (ō = o), spaces, apostrophes and hyphens, and tolerates typos: none in a query under 5 letters, one from 5, two from 9 (edit distance to any part of the title, the artist, or artist + title). Closer matches come first, at most 20. They show at once, above a spinner while YouTube's results load, and keep their place when those arrive.

## Implementation notes (2026-10-24)

Decisions taken while building v1, where the spec left room or turned out different:

- Licences: Metrolist innertube, InnerTubeX and QuackJS are GPL-3.0 (all three vendored in `core`); Sudachi, SudachiDict and Media3 are Apache-2.0. The app is GPL-3.0 (LICENSE).
- Japanese dictionary (2026-10-24). Sudachi 0.8.2 (`com.worksap.nlp:sudachi`) with SudachiDict core, version 20261015.
  - Why: Kuromoji's IPADIC mis-split all-hiragana text (よふかしのうた → "Yo fuka shinōta"), 二人 ("ninin") and katakana loanwords (セブンティーン). Kuromoji UniDic splits right but adds 179 MB of heap. SudachiDict splits right and is memory-mapped: about 80 ms to load on the JVM, almost no heap. Core, not small: small split compounds such as お母さん, 一歩 and 既視感 and needed a hand-made word list; core gets them from the dictionary (the user ruled out word lists, see Rules).
  - Licence: SudachiDict is Apache-2.0. Its lexicon and connection matrix contain parts of UniDic (BSD 3-clause, © The UniDic Consortium). The core lexicon also contains parts of mecab-unidic-NEologd (Apache-2.0, © Toshinori Sato; built partly from Hatena keyword data). Both are compatible with GPL-3. The notice ships in the dictionary APK as `assets/sudachi-LEGAL.txt`, with the Apache-2.0 text (`LICENSE-2.0.txt`) and `NOTICE`, which says the dictionary is modified from SudachiDict and how (Apache-2.0 §4 (a) and (b)); the dict build fails when `NOTICE` names another SudachiDict version. roma's APK has `assets/NOTICE`, `LICENSE-2.0.txt` and `CDDL+GPL-1.1.txt` for Sudachi and jdartsclone (Apache-2.0, their jars carry no licence file) and javax.json 1.1.4 (CDDL 1.1 or GPL 2 with the Classpath Exception; roma uses the GPL option, CDDL doesn't combine with GPL code). Its `NOTICE` also names the files roma modified from Sudachi's (roma-unk.def, roma-sudachi.json, RomaLattice). GPL 2 §3: each release carries `javax.json-1.1.4-sources.jar` from Maven Central, checked against its sha256 (release.yml). Upstream Sudachi and SudachiDict have no NOTICE file to pass on.
  - Size: SudachiDict core is 202 MB; roma ships a slim build of it, 62 MB (107 MB until 2026-10-27), stored uncompressed in the dictionary APK (`noCompress += "dic"`).
  - Slim dictionary (2026-10-25, `:dict-tool`, task `:core:sudachiSlim`): SudachiDict is built for search engines, and roma only reads a word's reading, part of speech and dictionary form in split mode C. The tool exports the official dictionary with Sudachi's `DictionaryPrinter` and rebuilds it with Sudachi's `DicBuilder`:
    - Postal addresses dropped: compound place names (with split data) of 5+ characters containing 都道府県市区町村郡 (465,443 of 1,630,049 entries, e.g. 京都府京都市上京区菊屋町). Short or famous names (富士山, 東京都) stay; dropping every compound place name split 富士山.
    - Split data (A, B, word structure), synonym groups and normalized forms cleared. Dictionary forms stay (word card; they cost about 2 MB).
    - Words that never win dropped (2026-10-27, 43,105 entries): a word is left out when another word with the same text costs less in every context, i.e. its cost plus the most its left and right connections can cost more (over the ids in use) is still below this word's cost. Both cover the same span, so the best path never contains it, and the unknown-word rules, which only ask whether some word starts at a position, see no change. Words another word names as its dictionary form stay. Splits into two words were also tried: 2,300 more entries, not worth the code.
    - Connection matrix: only the ids still in use (words, unknown-word definitions, config, 0), with identical rows and columns merged (5981² → 4146², every cost unchanged). It stays square: Sudachi's builder checks a word's left id against the size its lookups use for right ids. Ids are renumbered; the class of id 0 stays 0 (sentence start and end), ids of -1 (entries only referenced) stay -1. ## Continuity (2026-10-25)

- Restart: `Playback` writes the queue (songs, sections, index, repeat, shuffle order, radio seed and continuation, mix ID and continuation) to filesDir/queue.json after each burst of queue changes, and "<videoId> <ms>" to filesDir/position on pause, seek and every 10 s while playing; both via tmp file + rename. At start the queue comes back paused, at its position, with lyrics from their cache; no Last.fm "now playing", and radio top-up and prefetch wait for Play. A fully cached song is prepared at once; any other on Play, so opening the app costs no data. The tab and the player view (song, lyrics, queue) come back too (prefs `ui.tab`, `ui.playerView`). An expired radio continuation restarts the radio's pages.
- Media buttons: the session's media button receiver (`MediaButtons`) starts `PlaybackService` as a foreground service and hands it the key, so a headset, car or the system's media controls resume after the process died. A headset's single button: one press plays or pauses, two quick presses skip. The system's "resume" after a restart browses the service's recent root (`EXTRA_RECENT`), which holds the song the saved queue stops at; neither the old Media3 build nor this one showed the resume card on the emulator.
- Network drops (`WaitForNetwork`): with no connection, loads retry every 2 s for up to 10 min and the error reaches the player only when that gives up, so the buffer plays out, the player shows "Waiting for network…" (no validated default network, buffering, play wanted) and goes on by itself. Other errors keep 3 retries. The Play slot follows `Util.shouldShowPlayButton`: Pause while buffering.
- Opt-in "Resume when headphones reconnect": a pause caused by audio becoming noisy is undone when a headset, A2DP/BLE, USB headset or hearing aid output appears within an hour (`AudioDeviceCallback`, no polling). Not testable on the emulator.
- Opt-in "Download songs ahead": the load control buffers the whole current song (up to 10 min, else 50 s), and the next 3 songs are cached in full with `CacheWriter`. The current song can't use CacheWriter: the player's open read locks the cache span. Queue rows say "saved" for songs fully in the cache.

- Signed out, home continuation pages come back empty unless every request carries the same visitor data; Home fetches one if none is stored.
- Playing a mix (tap on its tile), or the Play button on any `RD…` playlist page: the songs go into "You queued" as a playlist, not radio. The radio filters (audio over video, duplicates, bans) apply; the leash doesn't (`filterMix`). The next page loads when 3 songs are left. Continuations of generated playlists loop back to songs already listed (an editorial list gives about 100 distinct songs over 6 pages, the Supermix about 137), so 3 pages with nothing new end the mix and radio follows, unless "stop when the queue ends" is on. The playlist page drops these repeats too.

## Getting songs ready before the tap (2026-10-25)

- A guess prepares a song the way a tap would: its stream URL and first 32 KB (`Playback.prepare`). Guessed: an opened album, playlist or artist page's first song (Play and the first row), Search's top row ("Seen before" first, then YouTube's top song), and the next three songs when the queue view opens. One at a time, at most 60 an hour; none while the current song is loading or a picked song is being prepared.
- Cost: about 45 KB a guess (a lookup of about 12 KB and 32 KB of audio; nothing for a song already cached), under 3 MB an hour at the cap, against about 60 MB an hour of audio. Battery: a few short requests, no timers or polling.
- Guesses run only on an unmetered network outside Battery Saver. The setting "Preload on mobile data" (off by default) lifts that.
- A song needed the InnerTubeX fallback in the last 7 days: the app start also warms that path (player script, cipher config, PoToken WebView) with that song, within the same network and battery limits. One lookup per start.
- Play on a generated playlist's page (RD…) plays the songs the page already holds instead of loading the playlist again; radio follows when they run out.
- Coming back to the foreground loads a Home older than 30 minutes again behind the shown one.

## Desktop (2026-10-29)

The Android app's screens and logic run on Linux and Windows, from the same source.

- Layout: `shared/src/main/kotlin` holds the screens, `Playback`, `Store`, `Images` and the PoToken logic, and is a source folder of both `:app` and `:desktop` (no Kotlin Multiplatform: the shared code uses the JDK freely, and the Android build is the same code as before). What differs per platform is a small set of functions and types with the same names in `app/…/Platform.kt` and `desktop/…/Platform.kt`: preferences (`Prefs`: SharedPreferences on Android, a properties file on the desktop), decoded pictures (`Pic`), toasts, links, share, Back, ICU (`android.icu` / ICU4J), the text field (EditText / Compose's), system colours, file pickers, the dictionary and updates, sign-in.
- The player sits behind `AudioPlayer` (shared), with Media3's names and constants: `ExoAudio` on Android passes each call to ExoPlayer, so the Android app plays as before. Measured on the 0.1.55 release build: APK +296 bytes (1,765,764 → 1,766,060, debug-signed), classes.dex +176 bytes; playback, skips, restart and the PoToken path (forced with `-Proma.refuseVisionOs=true`, WEB_REMIX past 1 MB) checked on the emulator. Cold start on the emulator (API 35, 2026-10-30), release builds under a test app ID, 22 alternating blocks of 6 starts, only blocks whose every start ran at load under 8: medians 369.5 ms (66 starts, master) and 364 ms (65), −1.5 %, 95 % interval −5.9 % to +1.9 %.
- Desktop player (`DesktopAudio`, `Media.kt`): no native media library. YouTube serves nearly every song as Opus in WebM; of 290 songs from 27 searches (2026-10-29) 287 had Opus and the other 2 only AAC (every song had AAC), and the AAC-only `kBbnPzFcty8` has no Opus from any client. So:
  - Opus: roma's WebM reader and Concentus (pure Java, a port of libopus). Against ffmpeg's decoder: the same sample counts from the start and after a seek, 68 dB SNR at 160 kbps; ffmpeg's decoder and libopus differ in as many frames (Opus's noise fill is random per decoder).
  - AAC: roma's MP4 reader (YouTube's fragmented MP4) hands ADTS frames to roma-aac, a static build of ffmpeg with only its AAC decoder (`tools/build-ffmpeg.sh`, LGPL, 1.4 MB on Linux, linked with musl so it runs on any distribution, 1.2 MB on Windows, cross-built with llvm-mingw), and reads PCM back. Bit-exact with ffmpeg (110 dB). Pure-Java AAC was tried and rejected: both JAAD forks are wrong in about 5% of frames (Fraunhofer's decoder and ffmpeg agree in every frame).
  - Output: the JDK's SourceDataLine. Streams go through an audio cache (cache/audio, 1 GB, oldest out), always with a Range header (without one googlevideo throttles to a trickle); the next song's first bytes are cached ahead, so songs follow without a gap. No connection: retried every 2 s for 10 minutes, as on Android.
  - `./gradlew :desktop:decodeCheck -Pfiles=…` compares the decoding with ffmpeg's (needs ffmpeg).
- PoTokens and sign-in need a Chromium: JavaFX's WebKit runs BotGuard, but YouTube refuses its tokens (403 past 1 MB); headless Chromium's and jsdom's pass, WebAssembly or not; a hand-made fake DOM doesn't. `Browser.kt` uses the system's Chromium-family browser with roma's own profile over the DevTools protocol (the JDK's WebSocket): the one that worked last time (`browser.worked`), else every one in order (oganesson, Helium, Chromium, Chrome, Brave, Vivaldi, Opera, Opera GX, Edge), skipping the one that failed, else CEF, only when no system browser starts at all. CEF isn't in the package, not even its Java side: on first need roma downloads jcefmaven and the jars it uses (about 3 MB from Maven Central, each checked against the SHA-256 pinned at build time, `BuildConfig.CEF_JARS`) and jcefmaven downloads CEF (about 150 MB). CEF runs in its own process (`roma --cef-host`, then `CefHost.kt` in a class loader over roma's jars and those), since CEF must start before anything opens a window. CEF 146, not 152, which exits at start on Linux (code 28). The BotGuard steps and the token rules are shared with Android (`BotGuard.kt`). Sign-in: a browser window on the Google sign-in page; when it reaches music.youtube.com with the account's cookies, roma takes them. `./gradlew :desktop:botGuardCheck [-Pcef]` checks the tokens where they matter.
- Known limit: a browser roma drives listens for DevTools on 127.0.0.1, so another program of the same user (or, on a shared machine, another user) could connect to it while it runs: the hidden BotGuard page for up to 5 idle minutes, the sign-in window while it is open. Chromium's pipe transport would avoid it, but the JDK can't hand a child process the extra file descriptors it needs.
- Not yet on the desktop: media keys and the system's media controls (MPRIS), system colours. Share copies the link. Last.fm's sign-in returns to a one-request server on localhost.
- Packages (finimal's approach): the release build is ProGuard-shrunk (Sudachi kept whole, it loads classes by name). ICU4J is cut to what transliteration reads (`icuSlim`: without locale data, zones, collation, names, line breaks and the word dictionaries but Thai's, which Any-Latin uses to split Thai into words), and ProGuard drops the classes transliteration doesn't reach: no reflection on that path, so no keep rules; the transliteration rules none of roma's transliterators load are zeroed (`icuRules`). 15.2 → 1.1 MB. `:desktop:icuCheck` runs every transliterator roma uses over every assigned code point with the full jar and the released one: identical output, also under Polish, Japanese and Thai default locales. Skia's library (on Windows its icudtl.dat) carries ICU's whole data (10.4 MB) for its text breaking; the build keeps line, word and character breaking (without the Chinese/Japanese word dictionary) and zeros the rest in place (`trimSkiaIcu`; Windows' icudtl.dat is cut short instead, 10.5 → 1.7 MB). `:desktop:skiaCheck` lays out and breaks every script's code points with the original and the trimmed library: identical. The cost: word steps (Ctrl+arrow, double-click) in Chinese or Japanese text move one character at a time. Linux: a .deb and an .rpm (`tools/linux-packages.sh`) on the distribution's Java 21+. Sizes: jpackage's .deb with its own Java 78.7 MB; on the system's Java 24.7 MB; with the slim ICU4J 18.9 MB; with CEF's Java side downloaded on need 16.0 MB (.rpm 15.5 MB); with ICU4J shrunk and Skia's ICU data trimmed 11.4 MB (.rpm 11.1 MB). Installed size against 0.1.57: /opt/roma 51.7 → 35.6 MB (−31 %), from deflated jars instead of stored ones (the .deb grows to about 13.4 MB, as xz can't compress them again), narrower ProGuard keep rules, no line numbers or generic signatures in the classes, and the musl roma-aac; the full .msi's Java is compressed (jlink's zip-6, 32 MB less, 10 ms more at start). Windows: a full .msi with its own Java, and a small .msi and .zip whose launcher (`packaging/windows/Launcher.cs`) finds Java 21+ or downloads Temurin's once (`tools/windows-packages.sh`). ## Process

- Local git repo. Don't create a GitHub repo or a signing key without asking the user.
- Build toolchain: mirror ~/dev/plainfin (AGP, Kotlin, Gradle, SDK at ~/Android/Sdk, JDK under ~/.local/share/JetBrains/Toolbox/apps/air/jbr). Read its build files first.
- Test on an emulator. Never install on the user's own devices without asking first.
- Leave one small runnable check per non-trivial piece: romanization (including the Japanese/Chinese decision), the lyrics parsers (LRC, enhanced LRC), queue filtering.

## Storage and backups (2026-10-25)

- User storage (filesDir, prefs) holds only what the user would lose: settings, the YouTube and Last.fm sign-ins, corrections, the queue and position, unsent scrobbles.
- Anything that can be fetched or rebuilt again sits in the cache, so Android may clear it: audio, art, lyrics, pages, the mixes row, the local search index, synced likes, stream notes. Android counts a file as cache by its group, which a renamed file keeps, so data moved out of filesDir is copied, not renamed.
- Backups: no cloud backup at all, sign-ins included. A transfer to a new phone over Android 12+'s device-to-device path (cable or direct Wi-Fi) takes user storage, so the sign-ins carry over. Android 8–11 backs up nothing (its one backup path also serves the cloud). Rules: res/xml/data_extraction_rules.xml, backup_rules.xml. Vendor clone tools (e.g. Huawei Phone Clone) may not follow these rules.
- Package size, 0.1.51 (2026-10-28): 1,972,651 to about 1,694,000 bytes (−14%), same features.
  - No Ktor: `roma.core.http` (Http.kt) sends every request through HttpURLConnection, as Ktor's Android engine did, with transparent gzip, a byte limit, an early stop for the streamed watch page, and a disconnect on cancellation. InnerTubeX builds its requests on a small `Request` (URL, headers, JSON body). Ktor's disk cache did nothing: the player script went through a separate client without it, and the API calls are POSTs. About 140 KB.
  - The innertube calls roma never makes are gone (uploads, playlist edits, subscriptions, podcasts, playback stats, transcripts, account lists), with their request and response models.
  - Text fields are Android's EditText in the outlined box (`OutlinedTextField`, Ui.kt): Compose's BasicTextField brought its text input, selection, magnifier and context menu, about 120 KB. Pixel-identical on the emulator, empty and typed. The EditText is made when the field is first on screen: made in a tab built hidden (`buildAhead`), it stayed blank the first time the tab was shown.
  - No native code: androidx.graphics.path's PathIterator library (9 KB) had no caller left after R8.
